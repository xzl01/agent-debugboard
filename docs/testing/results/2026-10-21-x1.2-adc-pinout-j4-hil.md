# x1.2 ADC, pinout, J4 serial and final combined-image HIL — 2026-10-21

## Verdict and scope

**PASS for the enumerated bounded digital/functional checks on the final
combined image.** An independent oracle found no release-blocking P0–P2 and
classified the single non-reproduced transient below as a P3 diagnostic
limitation. This run consolidates the current eight-channel ADC contract,
x1.2 connector metadata, MCU-owned J4 transports, embedded xterm.js UI, logic
analyzer/J4 restoration, normal reboot and mandatory startup sequence.

This is not full electrical certification. The limitations and transparent
transient sections are part of the verdict and must travel with any citation of
this report.

## Startup, persistent replay and mandatory first mutations

The saved configuration replayed `5v_out=on` and `vdd_5v=on` before HTTP became
ready. This was recorded as persistent replay, not misreported as a Device Tree
boot default.

After the control transport became ready:

1. The first host hardware mutation explicitly set/confirmed `5v_out=on`.
2. The second host hardware mutation requested fixed PD 20 V.
3. Only then did the run continue to INA226 and other functional checks.

PD status was available and active at gear 4, fixed 20 V, maximum 3250 mA. The
capability catalog contained five fixed profiles plus PPS. Status register raw
value `0x88` carried a reserved/unknown bit: firmware logged one warning, kept
the successful I2C sample authoritative, ignored the unknown bit for protocol
validity, and did not enter retry/recovery or warning spam.

The enabled 5 V INA226 reported approximately 5.1 V with valid current data.

- ADC0 retained `PD input divider; ADC pad voltage`; no host `115/15`

## x1.2 connector and GPIO metadata

The static connector catalog contained 24 physical cells and nine mapped
safe-control/monitor cells. Runtime GPIO surfaces contained exactly those nine
controls; GP17 and GP18 were absent rather than fabricated. GP29/ADC3 was
present and input-only.

The embedded UI and API agreed on:

- J8/right/order 0 and J13/right/order 1;
- GP12–GP16 and GP29 on J8, GP7–GP9 on J13;
- no GP17/GP18 controls in either connector or generic groups;
- inert GND/non-control cells;
- USB mux and TF switch labels derived from the firmware net/catalog metadata,
  not guessed host mappings.

The embedded Web UI was exercised against the real board. A Web/API action
drove GP7 HIGH and the final action restored GP7 to INPUT. This run did not
capture independent visual evidence of a red filled-circle rendering.

## J4 serial transports

J4 was verified as one MCU-owned logical serial port backed by UART1, not as a
host-broker or dual-channel serial product.

### Embedded Web terminal

- The production page on the board auto-created a live session and subscribed
  to `serial.j4`.
- xterm.js connected to a real Linux target console and completed bidirectional
  terminal traffic.
- Manual disconnect stayed disconnected without a retry storm; explicit
  reconnect restored the session.
- A WebSocket PING carrying payload bytes `00 ff` received a PONG with the
  identical two bytes on the board, and the connection remained usable for J4
  traffic afterward.
- Binary NUL/`0xff`, final-frame assembly and the 480-byte admission boundary
  retained their offline protocol coverage on the exact final source.

Port 5173 was also used for development-preview testing, but it is not the
product transport. The embedded port-80 UI and MCU WebSocket were tested
separately and are the product evidence.

### Fan-out and completion ownership

The final run exercised J4 CDC ACM4, a `serial.j4` WebSocket, and two raw-TCP
5555 clients concurrently. One TCP client was connected and intentionally left
unread while the fast sinks continued receiving. These were four concurrent J4
sinks in total: CDC, WS, TCP0 and TCP1.

- Fast sinks continued receiving, but the board run did not generate enough
  traffic to observe or increment the unread sink's drop counter.
- WS writes emitted `serial_write_accepted`, followed by the matching
  `serial_write_complete` after physical UART wire completion.
- Raw TCP listened on `0.0.0.0:5555` and remained binary-transparent; no
  Telnet/IAC negotiation, banner, echo, or CR/LF conversion occurred.
- J4 state/config generation and sink/queue counters were visible through
  `GET /api/v1/serial/j4`; configuration CAS behavior passed.

Offline production-helper tests on the exact final source cover forced
slow-sink overwrite/drop accounting, partial sends/EAGAIN, and disconnect/slot
reuse without stale completion delivery. Those cases are not relabeled here as
observed board evidence.

## Logic analyzer and J4 restoration

Native sigrok listened on raw TCP 5556. An initial image incorrectly bound the
listener to the previous fixed subnet and failed after the board restored
subnet 201. The listener was changed to `0.0.0.0:5556`; the final image passed
on `172.29.201.1`.

Final SINGLE capture evidence:

- physical source: GP10;
- rate: 100 kHz;
- requested duration: 2 s;
- received: 13 data frames and 212992 samples;
- capture completed with J4 paused during pin ownership and operational again
  after terminal cleanup restored UART1.

The run also verified J4 normal traffic before/after capture. It did not execute
the worst-case active 480-byte frame at 9600 baud through the bounded
wire-complete pause timeout; that branch remains host-model-only evidence.

## Normal reboot and post-reboot safety

Normal HTTP reboot was repeated on the final image without enumerating

boundary, the first host mutation again confirmed `5v_out=on`, the second
requested PD 20 V, and the final INA226 validation passed. The watchdog returned

reboot cases.

## Transparent post-reboot PD/NCM transient

One diagnostic anomaly occurred after one of the final normal reboots and is
not hidden by the PASS rows above:

1. The fixed-PD 20 V PUT succeeded and the following GET reported 20 V.
2. A subsequent ADC HTTP request failed at the host with NCM `ECONNRESET`.
3. A later status read at the **same MCU uptime** reported `available=true`,
   `pd_active=true`, and `last_error=0`, but the requested-voltage state and
   capability cache had been cleared.
4. No second MCU reboot and no corresponding MCU error log were observed.

The later PD snapshot is consistent with an earlier PD gate, ADC, I2C, or
status-path error that invalidated firmware-owned request state, followed by
successful reprobe. It does not establish that sequence as the root cause:
successful probe/status processing clears the live `last_error`, and no
transition log captured the original errno. Source review found no USB/NCM
reset path that clears PD state, so the host-side `ECONNRESET` is temporally
adjacent only; independence or a common cause remains unresolved.

`voltage_mv=0` means that the requested voltage is unknown to firmware. It does
not mean measured 0 V or a hardware fallback to 5 V. ADC0 remained
approximately 2.485 V while the physical source remained at 20 V. Firmware
intentionally does not replay the old request after recovery.

The transient did not reproduce in the following bounded attempts:

- re-PUT fixed 20 V, then 100 status polls over 11.3 seconds: stable;
- 250 Hz ADC recording, 1,619 samples plus 100 status polls over 8.6 seconds:
  stable;
- a second normal reboot, first status at uptime 1.424 seconds, then 100 status
  polls over 6.34 seconds: stable.

Final INA226 rail data and watchdog healthy/armed checks passed after those
attempts. The independent oracle found no release-blocking P0, P1, or P2 and
accepted the event as one bounded, non-reproduced P3 diagnostic limitation.
Recurrence under nominal operation, persistent transport failure, or evidence
of incorrect physical voltage reopens it as P2.

## Initial failures fixed before the final PASS

Two failures occurred on earlier images and are not hidden by the final verdict:

1. PD status raw `0x88` failed an over-strict bit-7 validator. The implementation
   was corrected to tolerate reserved bits, warn once, and retain a valid I2C
   read.
2. Native sigrok 5556 bound the wrong fixed subnet after persistent subnet 201
   replay. Both J4 raw TCP and sigrok now bind all local IPv4 addresses; the
   final image passed on `eth1` / `172.29.201.1`.

## Limitations and explicitly unperformed checks

The following are **not passed** by this report:

- ADC0 real PD-source physical unplug/replug and the approximately 100 ms
  automatic monitor/reprobe path were not performed.
- Actual stuck-line electrical fault injection was not performed because no
  unsafe external SDA/SCL pull was authorized.
- 50 ns spike behavior, analog rise time, VOL, powered-off Ioff and back-power
  paths were not certified.
- The J4 pause path was board-tested with idle/normal traffic, but the active
  worst-case 480-byte payload at 9600 baud and timeout/cancel boundary was only
  host-tested.
- CDC LOW/HIGH/reset coalescing was sanitizer-tested on the host only because
  `rustty` retained tty ownership during the board session.
- The single PD/NCM `ECONNRESET` transient was not reproduced or root-caused;
  it remains an accepted P3 observability limitation and must be reopened as P2
  if it recurs under nominal operation.
- TUI rendering and control behavior passed 629 Rust tests and production CLI
  operation, but this run did not independently photograph a manual TUI visual
  session.

Consequently this report is functional HIL evidence for the enumerated final
image, not a claim of complete electrical, timing, UI-visual, or fault-injection
certification.
