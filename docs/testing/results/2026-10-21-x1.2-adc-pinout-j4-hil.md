# x1.2 ADC, pinout, five-output power, J4 serial and final combined-image HIL — 2026-10-21–22

## Verdict and scope

**PASS for the enumerated bounded digital/functional checks on the final
combined image.** An independent oracle found no release-blocking P0–P2 and
classified the single non-reproduced transient below as a P3 diagnostic
limitation. This run consolidates the current eight-channel ADC contract,
x1.2 connector metadata, the five-entry power-output catalog including the
`vdd_5v`-child `5v_usb_hub`, MCU-owned J4 transports, the finite automatic
terminal-responder matrix, the 4800..115200 UART product ceiling with separate
high-rate diagnostics, CDC line-coding staging/promotion behavior, embedded
xterm.js UI, logic analyzer/J4 restoration, normal reboot and mandatory startup
sequence.

This is not full electrical certification. The limitations and transparent
transient sections are part of the verdict and must travel with any citation of
this report.

## x1.2 connector and GPIO metadata

The static connector catalog contained 24 physical cells: 11 safe controls and
13 inert cells. Ten controls were output-capable; GP29/ADC3 was input-only.
Runtime GPIO surfaces exposed exactly GP5/GP6/GP7/GP8/GP9/GP12/GP13/GP14/GP15/
GP16/GP29; GP17 and GP18 were absent.

The embedded UI and API agreed on:

- J8/right/order 0 and J13/right/order 1;
- GP5, GP6, GP12–GP16 and GP29 on J8, GP7–GP9 on J13;
- no GP17/GP18 controls in either connector or generic groups;
- inert GND/non-control cells;
- GP5 at J8 pin16/`GPIO5_CON` and GP6 at J8 pin15/`GPIO6_CON`, both ordinary
  direct RP2354 GPIOs rather than USBMUX/TF-switch controls;
- J8 pin20 as the `5V_USB_HUB` power contact, not a GPIO/ADC control;
- the five-entry power-output catalog including the `vdd_5v`-child
  `5v_usb_hub` output.

Both HTTP API and embedded Web actions exercised GP5 and GP6 through
input→HIGH→LOW→input with authoritative readback after each transition. Their
default/restored state was input; the hardware contract specifies no pulls. A
separate Web/API action drove GP7 HIGH and restored GP7 to INPUT; this run did
not capture independent visual evidence of a red filled-circle rendering.

### Switch and persistent-configuration catalog

The x1.2 switch catalog contained only `sd` and `tf_wp`. `switch/sd` was tied to
MCU GPIO4 / `GP06_TF_SW`; TF write protection used GPIO22. Each was moved to its
alternate legal value and restored, with no change to GP5, GP6, or the
`vdd_5v` parent rail. `GET /api/v1/switch/usb` returned HTTP 404, and status,
config and WS
surfaces contained no USB switch.

The v1 config catalog contained 18 entries and encoded to at most 84 bytes:
five power outputs, two switches and eleven GPIOs. `power/5v_usb_hub` was a
normal fifth power item; old `switch/usb`, `gpio/GP17` and `gpio/GP18` IDs were
rejected rather than aliased, and a v1 record containing a removed ID was
malformed rather than migrated. A snapshot saving GP5/GP6 as input replayed
successfully over normal reboot. After that check, the pre-run persistent
snapshot containing `5v_out` and `vdd_5v` was restored.

### Hub output and parent-child behavior

`GET /api/v1/power`, `/api/v1/status`, and `GET /api/v1/config` all advertised
the fifth output `5v_usb_hub` with GPIO24 / `GPIO24_USB_CRL`. The HTTP and Web
surfaces read back the actual off state; no client-side default was used.
Observed behavior:

- enabling `5v_usb_hub` from a state with `vdd_5v` off enabled `vdd_5v` first,
  and GET then reported both on;
- disabling `5v_usb_hub` left `vdd_5v` on;
- disabling `vdd_5v` turned `5v_usb_hub` off first and then the parent, with both
  reading off;
- enabling `vdd_5v` alone did not enable `5v_usb_hub`;
- a child-only `power/5v_usb_hub` snapshot replayed across normal reboot with
  parent-before-child ordering, and GET reported both on.

Physical downstream power was verified rather than inferred from GPIO/API state:

- with `5v_usb_hub` off, bounded `lsusb` polling showed no `067b:2731`;
- after enabling `5v_usb_hub`, the same bounded poll enumerated
  `067b:2731 Prolific Technology, Inc. USB SD Card Reader`;
- disabling `5v_usb_hub` removed that device, and a second enable recreated the
  same `067b:2731` reader;
- the card reader was not mounted, read, or written.

This confirms that U38 / `5V_USB_HUB` actually supplies downstream hub VBUS, not
merely that the GPIO or API state changed. At final cleanup GP5/GP6 were input
after input→HIGH→LOW→input, `switch/sd` was `target`, `switch/tf_wp` was
`writable`, `5v_usb_hub` was off, and the `vdd_5v` parent remained on.

`5v_usb_hub` correctly had no INA226/ADC descriptor. `/api/v1/adc/read` remained
the eight-channel contract; `vdd_5v` stayed the parent total and was not used as
a synthetic hub-current measurement. The final state restored the pre-run v1
snapshot with `5v_out=on`, `vdd_5v=on`, and `5v_usb_hub=off`.

### CDC line-coding staging and promotion

Firmware internally distinguishes CDC line-control states DOWN, PROMOTING, UP,
and BLOCKED. These names and block reasons are internal; the external
`/api/v1/serial/j4` response does not expose a phase or reason field. Its `dtr`
field is the published CDC/gate state, not the raw physical sample.

On the final image:

- after flashing/reboot with no host CDC connection, `usb_configured` became
  true and GET still reported `115200`, `dtr=false`, and zero sinks after 4
  seconds; the earlier image's change to `9600` was not observed;
- with DTR false, an HTTP line-coding request for `5200` applied immediately and
  succeeded; WS uses the same immediate worker path. USB default line-coding
  notifications in this LOW state only stage a candidate tuple and do not change
  active line coding or generation;
- opening the real ACM4 at `115200` first showed active `115200` and then
  published `dtr=true`; `uname -s` on the target returned cleanly;
- closing ACM4 left GET at `115200` three seconds later;
- a TCP SINGLE 100 kHz / 2 s logic-analyzer capture passed while J4 remained at
  `115200`.

On LOW→HIGH, firmware first applies any staged USB tuple and observes
completion/rollback before publishing DTR and opening CDC ingress. A failed
apply, attach, or detach enters BLOCKED and keeps DTR/ingress closed until a
successful LOW/reset boundary (with safe same-LOW recovery for the specific
unknown-LOW and detach-failure reasons). Each USB notification increments a
sequence before the HAL read and stays inflight until its complete state commit;
promotion requires an unchanged sequence and zero inflight notifications. The
mailbox/staged attempt is tagged with a session epoch and the worker validates
that identity before applying, so a stale attempt cannot cross a LOW/reset.
Deferred USB notification handling is a production prerequisite: notification
callbacks only stage/commit state and wake the control worker, never performing
physical attach, promotion, or HAL configuration in notification context.

- WS writes emitted `serial_write_accepted`, followed by the matching
  `serial_write_complete` after physical UART wire completion.
- Raw TCP listened on `0.0.0.0:5555` and remained binary-transparent; no

- J4 state/config generation and sink/queue counters were visible through

### Automatic terminal responder matrix

Explicit J4 input remained multiwriter: a client not selected for automatic
replies was not read-only and did not acquire TX ownership. The controlled
target tty was used to emit terminal position/attribute queries and to capture
every reply. The final image produced:

| Attached clients | Automatic responder | Observed result |
| --- | --- | --- |
| one Web, no CDC DTR | that Web slot | exactly one `ESC[2;1R` |
| two Web, no CDC DTR | lowest Web slot | exactly one `ESC[2;1R` |
| Web + CDC DTR | CDC | only CDC `ESC[24;80R`; no Web reply |
| passive Web manual key `x` | other client or none | target received `0x78` |

The non-selected Web page in the two-Web case remained an observer for automatic
replies, not a read-only client: the passive manual-key row confirms explicit
input still reached the target, and IME/paste use the same explicit input path.
No ANSI or other escape-sequence filtering was applied to target or host data.
State/data epoch barriers, a renderer rebuild on generation changes, and the
responder-promotion queue plus a local ECMA-48 CAN parser fence prevented a
passive page's stale partial or queued query from being answered after
promotion. CAN was consumed only by xterm's local parser and was never sent to
the UART or included in the RX log.

This matrix is finite functional evidence for the four listed topologies. It is
not an exhaustive test of every terminal escape sequence, every multi-client
race, or every IME/browser combination.

### Supported baud range and ownership

Using the same open J4 CDC file descriptor, host SET_LINE_CODING and subsequent
authoritative GET status observed:

`115200 → custom 5200 → 4800 → 115200`.

The CDC shell remained clean. This demonstrates that 4800..115200 is a
continuous integer range; the five UI presets (9600/19200/38400/57600/115200)
are recommendations only. HTTP
requests above the cap were rejected: 115201 returned 400 and left the current
tuple unchanged, and the product firmware does not accept 230400, 921600, or
1500000.

While DTR held CDC configuration ownership, HTTP CAS admission was asynchronous
and completed with `result=-16`; tuple and generation remained unchanged. After
DTR release, custom 5200 applied and 115200 was restored. Because the USB
control transfer cannot report the later application rejection,
`/api/v1/serial/j4` current/generation remained the authority.

At 4800 baud with 8E2 framing, a 480-zero-byte TX was accepted and reached
physical wire completion in 1.213 seconds. The bounded host write deadline was
derived from the eight-slot queue plus a 2-second margin.

The target peer was `radxa@192.168.2.163` after DHCP renewal, with J4 connected to
`/dev/ttyAS0`. Its serial getty was stopped temporarily, both endpoints were
put in raw 8N1 mode, and deterministic pseudorandom payloads were compared bit
for bit in both directions. The original tty settings and active getty were
restored afterward.

| Baud | Bytes per direction | Bits per direction | Tested bits, both directions | Bit errors |
| ---: | ---: | ---: | ---: | ---: |
| 4800 | 8192 | 65536 | 131072 | 0 |
| 5200 | 8192 | 65536 | 131072 | 0 |
| 115200 | 131072 | 1048576 | 2097152 | 0 |

The final-image supported-rate aggregate was **2,359,296 tested bits, zero
observed bit errors (BER=0 for this finite sample)**. One earlier attempt was interrupted by
an operator-initiated peer reboot and serial operation that disconnected the
whole USB path; that interrupted sample was excluded and the supported-rate

and the watchdog healthy.

### High-rate diagnostics and support cap

The rates above 115200 are **not supported product rates**. The following
samples came from diagnostic runs outside the product cap and are retained only
as diagnostics that motivated the cap, not as PASS rows and not as part of the
supported-rate BER aggregate:

- 230400: the final physical diagnostic sent repeated `0x55`, and the peer read
  mostly `0xB5`/`0x95`, with significant framing errors.
- 921600: runs were unreliable and could not establish a stable synchronized
  sample.
- 1500000: runs were unreliable. One earlier sample showed zero errors but was
  not repeatable; a later run recorded 560 bit errors, and high-rate runs could
  not synchronize reliably.

No oscilloscope or external logic-analyzer bit-width measurement was performed;
these are tty-level byte/framing diagnostics, not analog signal-integrity
certification.

## Transparent post-reboot PD/NCM transient

One diagnostic anomaly occurred after one of the final normal reboots and is
not hidden by the PASS rows above:

1. The fixed-PD 20 V PUT succeeded and the following GET reported 20 V.
2. A subsequent ADC HTTP request failed at the host with NCM `ECONNRESET`.
3. A later status read at the **same MCU uptime** reported `available=true`,
   `pd_active=true`, and `last_error=0`, but the requested-voltage state and
   capability cache had been cleared.
4. No second MCU reboot and no corresponding MCU error log were observed.

The later PD snapshot is consistent with an earlier PD gate, ADC, I2C, or
status-path error that invalidated firmware-owned request state, followed by
successful reprobe. It does not establish that sequence as the root cause:
successful probe/status processing clears the live `last_error`, and no
transition log captured the original errno. Source review found no USB/NCM
reset path that clears PD state, so the host-side `ECONNRESET` is temporally
adjacent only; independence or a common cause remains unresolved.

`voltage_mv=0` means that the requested voltage is unknown to firmware. It does
not mean measured 0 V or a hardware fallback to 5 V. ADC0 remained
approximately 2.485 V while the physical source remained at 20 V. Firmware
intentionally does not replay the old request after recovery.

The transient did not reproduce in the following bounded attempts:

- re-PUT fixed 20 V, then 100 status polls over 11.3 seconds: stable;
- 250 Hz ADC recording, 1,619 samples plus 100 status polls over 8.6 seconds:
  stable;
- a second normal reboot, first status at uptime 1.424 seconds, then 100 status
  polls over 6.34 seconds: stable.

Final INA226 rail data and watchdog healthy/armed checks passed after those
attempts. The independent oracle found no release-blocking P0, P1, or P2 and
accepted the event as one bounded, non-reproduced P3 diagnostic limitation.
Recurrence under nominal operation, persistent transport failure, or evidence
of incorrect physical voltage reopens it as P2.

## Initial failures fixed before the final PASS

Three failures occurred on earlier images and are not hidden by the final
verdict:

1. PD status raw `0x88` failed an over-strict bit-7 validator. The implementation
   was corrected to tolerate reserved bits, warn once, and retain a valid I2C
   read.
2. Native sigrok 5556 bound the wrong fixed subnet after persistent subnet 201
   replay. Both J4 raw TCP and sigrok now bind all local IPv4 addresses; the
   final image passed on `eth1` / `172.29.201.1`.
3. An earlier image let a USB default line-coding notification while DTR was
   false change the active rate to `9600`. The final image stages that tuple
   without changing active line coding or generation; a no-host reboot remained
   at `115200` after 4 seconds.

## Limitations and explicitly unperformed checks

The following are **not passed** by this report:

- ADC0 real PD-source physical unplug/replug and the approximately 100 ms
  automatic monitor/reprobe path were not performed.
- Actual stuck-line electrical fault injection was not performed because no
  unsafe external SDA/SCL pull was authorized.
- 50 ns spike behavior, analog rise time, VOL, powered-off Ioff and back-power
  paths were not certified.
- The active 480-byte 8E2 payload at 4800 baud completed physically in 1.213s
  before LA pause; only the actual 1250ms timeout/cancel branch remains
  host-tested.
- The zero-error UART aggregate covers supported rates only: a finite
  2,359,296-bit sample at 4800, 5200, and 115200. It is not a statistical BER
  guarantee or analog signal-integrity certification.
- High-rate operation is not a supported product path. The 230400 diagnostic
  produced mostly `0xB5`/`0x95` with framing errors, and 921600/1500000 runs
  failed to synchronize reliably; one earlier zero-error 1500000 sample was not
  repeatable, while a later 1500000 run recorded 560 bit errors. No oscilloscope
  bit-width measurement was made.
- The hub output was validated at the digital/functional level, including
  physical downstream enumeration. `5v_usb_hub` has no INA226 or ADC channel, so
  this run did not measure hub-branch current, inrush, or the card reader's
  media; the reader was not mounted, read, or written.
- The automatic-responder matrix covers the four listed topologies with one
  controlled target tty. It does not prove exhaustive terminal-query coverage,
  every browser/IME path, or every possible multi-client interleaving.
- Real ACM4 open/close, LOW-state HTTP apply, and the no-host `115200` default
  were board-tested. Rapid USB notification coalescing and reset races remain
  host-model/sanitizer coverage rather than a board control-line claim.
- The single PD/NCM `ECONNRESET` transient was not reproduced or root-caused;
  it remains an accepted P3 observability limitation and must be reopened as P2
  if it recurs under nominal operation.
- TUI rendering and control behavior passed 637 Rust tests and production CLI
  operation, but this run did not independently photograph a manual TUI visual
  session.

Consequently this report is functional HIL evidence for the enumerated final
image, not a claim of complete electrical, timing, UI-visual, or fault-injection
certification.
